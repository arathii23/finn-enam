# FINN followed-company phone alerts

Users open **Alerts**, choose companies and filing types, and select **Set up my phone**. FINN creates one random ntfy topic for that setup. The user subscribes to it in the free ntfy iPhone or Android app, queues a test, waits for the delivery worker, and confirms receipt to enable filing alerts. Changing the chosen companies reuses the same topic. Every user manages their own setup through an anonymous access code saved in their browser.

## What the feature covers

- The 15 companies in FINN's configured portfolio. The page lists the available company names and symbols and supports search.
- Results, major business changes, dividends/share changes, and earnings calls. These are selections over the existing NSE metadata classification. Each notification quotes the original subject and provides its date and source link.
- One source refresh shared across subscribers. Every subscriber is filtered by company, filing type, subscription start time and successful source checks. Identical attachments on NSE mirrors share a delivery identity.
- New follows, new filing types and resumed subscriptions start at the time of the change. Previously accepted filings are recorded separately for each subscriber.
- Matching filings are bundled into up to three notifications per device per UTC day. Each notification contains up to five filings. There is a shared 200-notification daily safety cap across tests and deliveries. Overflow remains pending within the seven-day source window.
- Pause and delete are available in the app. Save the access code to restore the setup in another browser. Each device's ntfy feed can be subscribed to from multiple phones using the same topic.

The ntfy topic is unlisted and randomly generated, with 192 bits of entropy. Anyone who obtains its name can read or post to it. Topics and access codes must be kept private. The user sees this explanation during setup. FINN sends public filings, and the original source remains the verification destination. [ntfy topic documentation](https://docs.ntfy.sh/publish/#picking-a-topic)

## One-time setup by the service owner

1. Create a Redis database on Upstash's **Free** plan. Its published allowance is 500,000 commands/month with 250 MB storage. Keep the Free plan selected. Obtain the REST URL and standard REST token. Add `UPSTASH_REDIS_REST_URL` and `UPSTASH_REDIS_REST_TOKEN` to the ignored local `.env` file for verification, then to the Render service's environment. Never add these values to code, frontend build variables, public data, screenshots or chat. [Upstash free plan](https://upstash.com/pricing/redis)
2. In the same Upstash account, open QStash and keep its **Free** plan selected. Add `QSTASH_TOKEN` and the exact `QSTASH_URL` shown in that console to the ignored local `.env`, then to Render. Add a random `FINN_PHONE_ALERTS_JOB_TOKEN` to both places. This private token authenticates the timer; it never appears in a public link. Redis credentials and QStash credentials are separate. QStash currently includes 1,000 delivery attempts/day and ten active schedules on its Free plan. [QStash pricing](https://upstash.com/pricing/qstash)
3. Deploy the backend and publish the frontend containing the Alerts tab. The static Pages app makes its alert requests to the existing HTTPS Render backend. CORS allows the Pages origin and the backend. Missing storage configuration is shown as awaiting activation, and saving is disabled.
4. Verify a real queued test through the configured QStash relay. FINN waits for a `DELIVERED` receipt from QStash before marking ntfy acceptance. Acceptance of a publish request alone is insufficient. Pending message IDs are retained privately in Redis and reused on the next check.
5. Complete a real user's setup on an iPhone. Check the lock-screen test, source link, selected-company delivery, changing choices, pausing, restoring from an access code, and deleting. Record actual phone receipt separately from ntfy acceptance.
6. After relay verification, run `PYTHONPATH=backend .venv/bin/python scripts/configure_phone_schedule.py --activate`. This creates or updates one named five-minute QStash schedule to the protected `/api/phone/tick` endpoint. The schedule allows one retry and a fourteen-minute response timeout for free hosting. Observe an actual automatic check in QStash and the catalog's `last_delivery_check` before claiming activation. The timer processes tests every pass and checks sources about every thirty minutes for active subscribers. Free services can delay a check.
7. Retain the GitHub worker as a manual fallback. It uses the two Redis values as private Actions secrets. Run **Check followed-company phone alerts** with dry-run selected to preview. Set `FINN_PHONE_ALERTS_ENABLED=0` after the independent timer is verified to avoid two automatic timers. Its original `NTFY_TOPIC` secret belongs to the earlier owner-only smoke test. Subscriber data stays in Redis; public snapshots and logs receive aggregate counts only. The QStash schedule can be paused in Upstash.

The timer normally uses 288 deliveries/day. FINN caps notification attempts at 200/day, with one relay retry per attempt. Even if both every timer and notification attempt use their one retry, these settings total at most 976 delivery attempts/day. This assumes this QStash account is not also serving other projects.

## Verification boundaries

The Redis store is independent of Render's filesystem and its seed corpus. Subscriber access uses a random 256-bit bearer code, hashed for record lookup. API responses containing settings are marked `Cache-Control: no-store`. Browser URLs contain neither access codes nor topics. User-supplied destinations are rejected. Test requests are explicit, coalesced while queued, and limited to five per day per setup. A request stays queued until its delivery is accepted. The page polls while waiting. Deleting the setup cancels its queued test. A notification already handed to an external relay may still arrive.

Subscription changes, deletion and dispatch share a per-record Redis lock. The dispatcher also has a global lock and a bounded run time. Accepted sends persist deduplication state per subscriber. A provider failure retains pending filings for a later check. An external service accepting a message and the subsequent Redis write cannot form one transaction. A crash or storage outage in that interval can cause a repeat on retry. This feature makes no exactly-once delivery guarantee.

The free ntfy service currently allows 250 messages per day per visitor. FINN reserves a lower allowance and bundles messages. These limits support an initial public pilot and can defer alerts when many users subscribe. Actual phone delivery, free-service capacity and scheduler timeliness require live observation. [ntfy limits](https://docs.ntfy.sh/publish/#limitations)

## Hosted verification on 18 November 2026

The feature is published on the existing Render and Pages URLs. Render remains on its Free plan. `FINN_PHONE_ALERTS_ENABLED=1` enables GitHub's schedule configuration. Real manually triggered worker run [44171277120](https://github.com/arathii23/finn-enam/actions/runs/44171277120) accepted the live browser's queued test, checked 15 of 15 NSE companies, and reported zero delivery failures. It found no new matching filings after the verification profiles' start times. This proves the manual pipeline; it does not prove the timer.

Two independent profiles were created and tested through the public API. Real ntfy retained-message checks verified their selected-company test messages. Their saved choices and topics persisted across backend redeployments. Hosted pause, resume, deletion, no-store response headers and Pages CORS were checked. The public Pages interface was exercised at iPhone width through search, multi-company selection, filing-type choices, queuing, automatic acceptance feedback and cleanup. The activation button stayed disabled until provider acceptance. Layouts fit 360, 390 and 430 pixels. Disposable verification subscriptions and access-code transfer files were removed.

To keep the free database allowance practical, the five-minute delivery pass reads a small index of queued tests. Full subscription snapshots are read for filing checks about every thirty minutes. Idle users require no individual record reads. Accepted filing identities retain the eight-day deduplication horizon needed for seven-day source checks. The dispatcher stops when the shared notification allowance is exhausted.

The original hosted failure was ntfy HTTP 429 on Render's shared egress. GitHub worker delivery was accepted successfully after the transport change. GitHub's native alert schedule produced no automatic run during more than an hour of observation; the existing price schedule also showed gaps of several hours. Canonical cron syntax and workflow reactivation did not establish regular runs. Automatic alerts cannot yet be called verified.

An optional QStash timer and delivery relay is prepared to address both limitations. It uses the same shared dispatch logic as the manual worker, with Redis locks and cadence controls. **Owner QStash credentials, real relay acceptance, a real automatic timer run and physical phone receipt are still required.** The QStash integration has only local simulated verification at this point. Keep this boundary explicit in submission claims.
